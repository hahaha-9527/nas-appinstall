# appinstall — NAS 本地应用安装器（铁牛OS / 铁牛NAS / ZeroNAS）

> 一个网页版的 `.tpk` 上传口子：把本地打包好的应用安装包传上去，自动注册进**应用中心**并完成安装 / 升级。

纯 Python 标准库实现（无需 pip 安装任何包），单容器、单端口（默认 8978），
页面支持拖拽上传、安装进度回显与一键卸载。已在 **Centerm Zero 1 Pro（铁牛OS）** 上实机运行。

## 功能特性

- **拖拽上传**：网页里直接把 `.tpk` 拖进去，回车即装，无需命令行。
- **自动注册 + 安装**：解析包内 `config.json`，写入应用中心数据库（图标、版本、大小、访问入口），再调用应用中心接口触发安装。
- **升级即"先卸后装"**：检测到已安装的同一应用时自动卸载旧版再装新版，避免端口与容器名冲突。
- **图标发布**：把应用图标同步到对外网页目录，手机 App 与远程网页也能正确显示图标（需配置公网前缀）。
- **启动自愈**：容器每次启动会把已上传应用的图标重新发布一遍，并修正数据库里残留的局域网图标地址。
- **卸载管理**：页面上直接对已上传应用执行卸载。
- **访问口令**：页面与写接口需要口令。`.tpk` 里的安装脚本是以 root 在宿主机跑的，
  "能打开这个页面"等价于"能以 root 执行任意命令"，所以 8978 不能裸奔。
  **装完第一次打开页面时自己设一个就行**，不需要 root、也不用去翻文件；登录后可随时改。
- **本地包库管理**：列出 NAS 上留存的全部 `.tpk`（含已卸载、未注册的），可下载、重装、
  删除（移入回收站而不是真删）。
- **环境自检**：一键检查包目录、数据库字段、应用中心接口、图标目录与回环访问，
  换 NAS 时用来看哪里不兼容。
- **页面署名**：页面底部一行 `© 2026 应用安装 v<版本> · Crafted by 西了个瓜`，
  版本号来自源码常量 `VERSION`，与 `config.json` 的 `version` 由打包脚本断言保持一致。

## 适用机型与系统

在 **Centerm Zero 1 Pro（铁牛OS）** 上开发并实机运行。本应用对接的是铁牛OS 自带的
应用中心（宿主机 `9004` 端口的 `appstoreApi` 与 `appstore.db`），所以"注册进应用中心并安装"
这一段只有在提供该服务的系统上才走得通：

| 平台 / 系统 | 支持情况 |
|---|---|
| **铁牛OS · 铁牛NAS · ZeroNAS**（Centerm Zero 系列） | ⭐ 原生支持：可在应用中心离线安装 `.tpk`，也可用 Docker Compose 部署；上传的包会自动注册进应用中心，并可启动 / 停止 / 卸载 |
| 其它带 Docker 的 x86 NAS（群晖 DSM / 威联通 QTS / TrueNAS / UNRAID / PVE / 自建） | ⚠️ 没有铁牛的应用中心服务时，"注册 + 安装"走不通；页面、访问闸门、本地包库与环境自检仍可用，自检页会直接指出是哪一项不通 |

> 应用中心本地安装、离线安装应用、Docker 应用上传安装、NAS 安装第三方应用。

## 环境要求

- 已安装 Docker / Docker Compose 的 x86 NAS（铁牛OS 原生支持）
- **host 网络**：安装器要访问宿主机 `127.0.0.1:9004` 的应用中心服务，端口也要直接对外
- 宿主机需存在应用中心服务与其数据库（铁牛OS 默认在 `/userdata/db/appstore.db`）
- 无需特权模式

## 安装步骤（铁牛OS / ZeroNAS）

### 1. 创建 Compose 项目

NAS 网页 → Docker → Compose 项目 → 新建，项目名 `appinstall`，
把 `docker-compose.yml` 的内容粘贴进去。

### 2. 上传程序文件

用文件管理器把 `app/` 目录（2 个文件）放到 Compose 项目目录下（即 `docker-compose.yml` 同级）。

### 3. 启动容器

在 Compose 项目里启动。日志出现下面这行即为成功：

```
TPK installer on 0.0.0.0:8978
```

### 4. 上传应用包

浏览器打开 `http://NAS_IP:8978`，把 `.tpk` 拖进虚线框，填写安装位置（默认 `/volume1`，必须是存储池路径），
点「上传并安装」。安装成功会直接显示版本与包体积；未完成时会显示应用中心里的实时状态。

### 5. 首次打开：自己设一个口令

浏览器打开 `http://NAS_IP:8978`，第一次会直接显示「设置访问口令」，自己定一个（至少 6 位）即可。
**不需要 root 权限，也不必去 NAS 上翻文件** —— 设完就进去了。

设好之后这个口子当场关上：以后打开只显示登录框；同一网络里的其它设备（访客手机、
被入侵的 IoT 设备）即使打开页面也装不了包。输一次记住 7 天（HttpOnly Cookie），
换浏览器或清缓存后需要再输一次。

想在部署时就定死口令，用 `TPK_PASSWORD` 指定（优先级最高，每次启动都以它为准）。
**应用中心自己来拉安装包不受影响** —— 那是从 NAS 本机回环发起的，已单独放行。

### 6. 验证

```
# 1) 登录取 cookie
curl -s -c /tmp/tpk.ck -H 'Content-Type: application/json' \
  -d '{"password":"你的口令"}' http://NAS_IP:8978/api/login

# 2) 带 cookie 上传安装
curl -s -b /tmp/tpk.ck -F 'file=@你的应用.tpk' http://NAS_IP:8978/api/upload
```

返回 `{"ok": true, "message": "...安装成功..."}` 即正常。

也可以用自带的一键验证脚本，把面板、闸门、未登录拦截、环境自检、已上传应用与
本地包库一次查完（退出码非 0 即有问题）：

```bash
python3 tools/verify.py http://NAS_IP:8978 你的口令
```

## 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `TPK_PORT` | `8978` | 面板监听端口 |
| `TPK_STORE` | `/userdata/tpk_local` | 上传的包与图标缓存目录 |
| `TPK_DB` | `/userdata/db/appstore.db` | 应用中心数据库文件路径（Docker 下由 `TPK_DB_DIR` 拼出） |
| `TPK_DB_DIR` | `/userdata/db` | 应用中心数据库所在目录（Docker 下同时用于挂载） |
| `TPK_APPSTORE_API` | `http://127.0.0.1:9004/appstoreApi` | 应用中心接口地址 |
| `TPK_DEFAULT_LOC` | `/volume1` | 安装位置下拉框默认值（存储池路径） |
| `TPK_WEBROOT` | `/usr/local/pc` | 对外网页目录，图标发布到这里 |
| `TPK_PUBLIC_BASE` | `https://tieniu.tieniu-link.com/pc` | 图标对外前缀。手机 App 与远程网页只认公网地址，用局域网地址会白图；显式填 `off` 关闭公网发布 |
| `TPK_PASSWORD` | 空 | 访问口令。留空则首次打开页面时由访问者自行设置（不需要 root）；填了则以它为准，每次启动覆盖页面上的设置 |
| `TPK_IMAGE_SIZE_KB` | `121437` | 应用中心"镜像大小"显示值，单位 KiB |

> 数据路径那三个（`TPK_STORE` / `TPK_DB_DIR` / `TPK_WEBROOT`）在 `docker-compose.yml`
> 里**同时**用于「程序读的环境变量」与「目录挂载」，两处取同一个值 —— 所以只能在
> `.env` 里整目录替换、容器内外路径相同；不设就走默认值，行为与以往完全一致。

## 访问口令

### 口令是怎么来的

按优先级：

1. 环境变量 `TPK_PASSWORD` —— 部署时固定，每次启动以它为准；
2. `$TPK_STORE/.auth.json` 里已有的记录 —— 页面上设置过、或从旧版本沿用下来的；
3. 都没有 → 页面进入「设置访问口令」状态，**由第一个打开页面的人设定**。

第 3 条是给**没有 root 权限的人**留的路。早期版本在这种情况下会随机生成口令写进
`$TPK_STORE/访问口令.txt`，而那个文件是 `root:root 600` —— 非 root 用户读不到，
页面又进不去，等于把自己锁在门外。现在只有显式设置 `TPK_PASSWORD` 时才写那个文件。

### 改口令

登录后页面底部有「访问口令」卡片：填当前口令 + 新口令即可。改完会重新生成会话密钥，
**其它设备上的登录立刻失效**，需要重新输一次 —— 这正是"口令可能泄露了要换掉"想要的效果。

### 忘了口令怎么办

口令按 PBKDF2 哈希存储，找不回来，只能重设：

- **有 root**：删掉 `$TPK_STORE/.auth.json`（即 `/userdata/tpk_local/.auth.json`）并重启容器，
  页面会回到「设置访问口令」；
- **有 root、想固定下来**：在 `.env` 里设 `TPK_PASSWORD=新口令` 再 `docker compose up -d`；
- **没有 root**：卸载重装**不会**重置口令（记录跟着数据目录走，这是有意为之，免得升级打扰），
  所以只能请有 root 权限的人做上面两条之一。

### 哪些路径需要登录

| 路径 | 要求 |
|---|---|
| `/`、`/favicon.ico`、`/icons/*` | 公开（图标被 `<img>` 直接引用，不带 Cookie 也得能读） |
| `/files/*` | 仅本机回环，或已登录者（回环放行是必需的，见下方说明） |
| `/api/*`（除 login/logout） | 必须登录 |

> **为什么 `/files/` 必须对回环放行**：应用中心安装时是靠自己访问
> `http://127.0.0.1:8978/files/<code>.tpk` 把包拉走的。如果这条也要求登录，
> 应用中心拿不到包，安装会静默失败 —— 表现是"提示安装成功但状态一直不变"。
> 这是给这个应用加鉴权时最容易踩的坑。

## 本地包库

「本地安装包」卡片列出 `$TPK_STORE` 下留存的全部 `.tpk`，包含已经卸载但包还在的、
以及从没注册过的。每个包显示应用名、版本、大小、上传时间、MD5 与应用中心里的实时状态。

- **下载** —— 把包取回本地
- **重装** —— 用留存的包重新走一遍安装（会先卸载当前版本）
- **删除** —— 移入 `$TPK_STORE/trash/`，不是真删，方便反悔。
  应用仍在运行或安装中时**不允许删除**，否则想重装时手里就没底包了

换新版包时，建议把旧包移进 `$TPK_STORE/_bak/<日期>/` 而不是直接覆盖 ——
**文件名或目录名以 `_` 开头的一律不会被列出**（`_upload.tpk` 这类中间文件同理），
所以归档目录放多少旧包都不会把面板弄乱。

> 这一点很要紧：包库是「重装」功能的唯一数据源。如果里面留着一个旧版包，
> 将来一次重装就可能把应用**降级**回旧版 —— 包括把已经清理掉的密钥、已经修掉的问题一起带回来。
> 换包后顺手在页面上核对一遍版本号和 MD5。

## 环境自检

页面底部「环境自检」点一下，逐项检查并给出结论：

| 检查项 | 说明 |
|---|---|
| 包目录可写 | `$TPK_STORE` 能否创建文件 |
| 应用中心数据库 | `appstore_app` 表字段是否齐全（缺字段会写出坏记录） |
| 应用中心接口 | `9004` 是否可达、已登记多少应用 |
| 图标对外目录 | `$TPK_WEBROOT` 与公网前缀是否配套 |
| 本机回环访问 | 应用中心拉包走的那条路是否通 |
| 访问闸门 | 口令状态与来源（待设置 / 页面上设置 / 环境变量） |

换 NAS、改过路径、或怀疑配置不对时，先跑一遍这个，比翻日志快。

## 改代码时注意：三份副本

`tpk_installer.py` 实际存在三份，**改一处漏一处会出很难查的问题**：

1. 本地源码 `app/tpk_installer.py`
2. 容器运行版 —— 应用中心装的 appinstall 容器在用的那份
3. 主机兜底版 —— 容器被卸载时，systemd 服务 `tie-niu-tpk-installer` 会用它接替

第 3 份最容易忘：漏了的话，卸掉容器后闸门和包库管理会一起消失。
用 `tools/check_sync.sh` 随时比对：

```
NAS_HOST=你的NAS地址 [NAS_PORT=22] [NAS_KEY=~/.ssh/id_ed25519] tools/check_sync.sh
```

连接信息从环境变量读，不写死在脚本里。

## 改页面时必须跑的两个检查

页面脚本是内嵌在 Python 里的（`PAGE` 是三引号字符串），有两个坑**光看接口发现不了**：

1. **转义被吃掉**：`PAGE` 是**非 raw** 字符串，源码里写 `\'` 运行时只剩 `'`，必须写 `\\'`。
   少一个反斜杠就会让内联 `onclick` 变成 `onclick="reinstall(''+p.code+'',this)"`，
   相邻字符串字面量 → 整个 `<script>` **语法错误** → 浏览器里一行 JS 都不执行：
   登录卡片不出现、列表永远停在「加载中」。而 `curl /api/list` 返回正常，
   从接口侧测一万遍也看不出来。
2. **部署了旧文件**：源码是对的，但线上跑的是上一版（忘了同步或忘了重启容器），
   症状与"代码写错"一模一样。

`tools/check_page.py` 就是为这两条准备的 —— 它把 `PAGE` 字面量交给 `ast.literal_eval`
求值（复现 Python 的转义处理，得到与运行时逐字节相同的 HTML），然后：

- 用 `node --check` 检查内嵌 JS 语法
- 核对 JS 里每个 `getElementById('x')` 都有对应的 `id="x"`
- 核对内联 `onclick` 调用的函数都定义过
- 扫描"被吃掉的转义"痕迹（`onclick` 里出现空的 `''`）

```bash
python3 tools/check_page.py                          # 检查源码
python3 tools/check_page.py --live http://NAS:8978   # 检查线上实际下发的页面
```

两处都要跑。想让检查更接近真实体验，可以用无头浏览器看一眼渲染结果：

```bash
chrome --headless=new --virtual-time-budget=9000 --dump-dom http://NAS:8978/ > dom.html
```

正确的现象：全新安装（还没设口令）时「设置访问口令」卡片可见；设过口令但没登录时是登录卡片可见，
两种情况四个功能卡片都隐藏。登录后反过来，并且两个表格里填满了应用与包的真实数据。

## 手机上用

页面已做窄屏适配（≤640px 生效）：表格改成一行一项、输入框与按钮铺满、字号放大到 16px
（iOS 在字号小于 16px 时会自动放大整个页面）。手机上直接输地址就能用，不需要额外设置。

**上传文件的两个坑，以及现在为什么不会再遇到**：

| 现象 | 原因 | 现在的做法 |
|---|---|---|
| 点上传区没反应 | `display:none` 的 file input 用 JS `.click()`，移动端会拦掉 | input 用 `opacity:0` 铺满整块区域，点到的就是 input 本身 |
| 一选文件浏览器就退回 | `accept=".tpk"` 是非标准扩展名，安卓解析 MIME 时崩 | 触屏设备上一律移除 `accept`，类型由服务端校验 |

少数环境仍可能传不了，通常是**宿主 App 的限制**而不是本程序：NAS 官方 App 内置打开的页面
（WebView）能不能选文件，取决于该 App 有没有实现文件选择回调。页面检测到触屏时会显示对应提示；
此时改用手机自带浏览器（Chrome / Safari / Edge）或电脑打开同一地址即可。

## 常见问题

**忘记口令 / 进不去页面？** → 见上方「访问口令」。口令是哈希存储、找不回来；删掉
`/userdata/tpk_local/.auth.json` 重启即可回到「设置访问口令」（这一步需要 root）。

**能不能不要口令？** → 不建议。没有口令时，同一网络里任何设备打开 8978 就能上传安装包，
而安装包里的脚本以 root 执行。如果你的 NAS 只在不对外、也没有任何访客设备的网络里，
可以接受这个风险，但本应用不提供关闭开关。

**重装了系统 / 换了 NAS，闸门还生效吗？** → 口令记录放在 `$TPK_STORE/.auth.json`，
跟着数据目录走；只带 `app/` 不带数据目录时，页面会回到「设置访问口令」，由第一个访问者重设。

**手机 App 里应用图标是白图？** → 图标必须走公网地址。把 `TPK_PUBLIC_BASE` 设成 NAS 的公网地址
（形如 `https://nas.example.com/pc`），并确认该地址下的 `/pc/` 确实指向容器挂载的 `/usr/local/pc`。
PC 内网看着正常、手机 App 白图，基本就是这个原因。

**上传后卡在"安装中"？** → 安装器只是把包交给应用中心，实际拉镜像与建容器由应用中心完成。
先在应用中心看进度；如果是镜像拉不下来，检查 NAS 的 Docker 镜像源。

**提示"应用中心返回: xxx"？** → 说明连不上应用中心服务。确认宿主机 `9004` 端口有服务在跑，
并且容器用的是 host 网络（默认已配）。

**重复上传同一个应用会怎样？** → 自动执行"先卸载旧版、再装新版"，配置目录按应用的约定保留。

**页面能打开，但列表一直显示"加载中"？** → 这是**浏览器端脚本没跑起来**，不是接口问题。
最常见的原因是内嵌 JS 有语法错误（见上方「改页面时必须跑的两个检查」），
也可能是浏览器缓存了旧页面 —— 先强制刷新（Ctrl/Cmd+Shift+R），
再跑 `tools/check_page.py --live <你的地址>` 确认线上页面本身是好的。

**换了存储池路径要改哪里？** → 改 `.env` 里的 `TPK_DEFAULT_LOC`，或在网页的安装位置输入框临时填写。

**升级安装器本身？** → 替换 `app/` 下的文件，`docker compose up -d` 重建容器即可。
